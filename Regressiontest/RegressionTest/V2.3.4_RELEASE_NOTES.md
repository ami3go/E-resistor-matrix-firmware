# E-Resistor Regression Test v2.3.4

## Reason for this release

A real `safe_output` run against firmware 0.4.4 returned valid channel masks using the format `0x0000`. Version 2.3.3 only accepted bare four-digit masks such as `0000`, so complete and safe HTTP/SCPI state responses were parsed as zero channels. This produced false failures in state validation, protocol consistency, concurrent polling, safe-output verification, and final cleanup.

## Corrections

- HTTP state parsing accepts both `ch1=0000 ...` and `ch1=0x0000 ...`.
- SCPI state parsing accepts both `CH1=0000,OPEN` and `CH1=0x0000,OPEN`.
- Parsed masks are always normalized to four uppercase hexadecimal digits without the prefix.
- Added tests using the exact eight-channel firmware 0.4.4 HTTP and SCPI response formats.
- State-related failures now retain raw and parsed responses for diagnosis.
- Stress failures include the complete raw SCPI response and parsed channel count.
- Safe-output and cleanup evidence includes raw `STATE?` text.


## SCPI transport hardening

The captured transcript also contained intermittent incomplete long replies (`"CH"` or an empty string). The client previously considered any 120 ms idle period to be end-of-response, even before a line terminator had arrived.

- Before CR/LF is received, fragmented SCPI replies now get a 750 ms inter-fragment window within the existing total timeout.
- After CR/LF, the original short drain window remains, preserving normal latency and collecting multi-line error replies.
- Eight-channel `STATE?` reads are validated and retried up to three times.
- A retry reconnects the SCPI socket when the previous read was empty or incomplete.
- Recovery attempts are written to `events.jsonl`.

## Evidence integrity

Version 2.3.3 generated `evidence_manifest.sha256` before deleting `RUN_INCOMPLETE` and before appending the final event. The resulting manifest was invalid immediately after a normal run.

Version 2.3.4 now:

1. Writes all reports.
2. Removes `RUN_INCOMPLETE`.
3. Creates `RUN_COMPLETE`.
4. Appends the final run event.
5. Generates the SHA-256 manifest.
6. Verifies every manifest entry before returning.
7. Avoids further ExtendedLogger writes after manifest generation.

This behavior is used by both the pure-Python runner and Robot Framework adapter.
